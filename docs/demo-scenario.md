# PXM 시연 시나리오

**대상**: 사내 연구소 구성원, 특히 개발팀장
**목적**: PXM이 지원하는 기능을 한 시나리오 안에서 전부 보여준다
**소요**: 30분 (단축 시 15분 구성은 문서 마지막 참고)

지원 기능 전체 목록은 `docs/features.md`, 시연 전 처리할 작업은 `docs/roadmap.md`에 있다.

---

## 설계 원칙

기능을 하나씩 나열하는 투어는 "그래서 뭐?"로 끝난다. 그래서 이 시나리오는
**업무 하나를 PXM에 처음 올리는 전 과정**을 따라간다. 관리자가 실제로 밟는 순서가 곧
기능 소개 순서이므로, 각 기능은 "다음 단계에 필요해서" 등장한다.

```
조직을 만들고 → 비밀정보를 넣고 → 흐름을 그리고 → 배포하고
→ 웹으로 실행해보고 → API로도 실행해보고 → 운영 화면에서 확인한다
```

**소재**: 협력사 직원의 사내 시스템 접근 권한 신청

이 소재를 고른 이유는 세 가지다.

1. 우리 접근제어 솔루션과 직결되어 청중이 맥락을 이미 안다
2. DB 조회, 데이터 가공, 조건 분기, 사람 승인, 외부 시스템 반영이 **자연스럽게 전부 필요하다**
3. 협력사 담당자가 등장하므로 외부 이메일 승인까지 억지 없이 들어간다

## 장면 1 — 조직 세우기 (2분)

> "PXM은 그룹 단위로 워크플로우와 권한을 격리합니다. 먼저 이 업무를 담당할 조직을 만듭니다."

**화면**: 플랫폼 설정 → 사용자 및 권한

**보여줄 것**
- 그룹 `보안운영팀` 생성
- 사용자 3명 생성과 역할 부여
  - `secadmin` — `group_manager` (워크플로우 설계·배포)
  - `approver1` — `user` (승인자)
  - `requester1` — `user` (신청자)
- 그룹 멤버 지정

**말할 것**: 역할은 `admin` / `group_manager` / `user` 세 가지이고, 워크플로우·자격증명·API Key가
전부 그룹에 묶인다. 다른 그룹의 리소스는 목록에도 나오지 않는다.

**미리 답할 것**: SSO/LDAP 연동은 아직 없다. 로컬 계정과 세션 인증만 지원한다.

---

## 장면 2 — 비밀정보 넣기 (2분)

> "워크플로우가 외부 시스템에 붙으려면 접속 정보가 필요합니다. 코드나 노드 설정에 직접 쓰지 않습니다."

**화면**: 플랫폼 설정 → 연동 자격증명

**보여줄 것**
- 자격증명 2개 등록
  - `hr-db` — 유형 `connection_string` (인사 DB 조회용)
  - `access-control-api` — 유형 `bearer_token` (접근제어 시스템 호출용)
- 저장 후 **목록에서 원문이 다시 보이지 않는 것**
- 자격증명 상세의 사용 이력(감사) 탭

**말할 것**: AES-256-GCM으로 암호화 저장하며 저장 후 원문 조회 경로가 없다. 노드에서는
`credential_id`로만 참조하고, 실행 시점에 Engine이 그룹 권한을 확인한 뒤 주입한다.
지원 유형은 `api_key`, `basic_auth`, `bearer_token`, `connection_string`, `ssh`, `custom`.

**강조점**: 자격증명을 쓴 것은 워크플로우가 아니라 **어느 노드가 언제 무엇을 썼는지**까지
감사 로그에 남는다. 이 부분이 접근제어 제품 관점에서 설득력이 있다.

## 장면 3 — 워크플로우 설계 (8분) ★ 본론

> "이제 흐름을 그립니다. 여러분이 지금 코드로 짜고 있는 그 분기가 이 그래프 하나입니다."

**화면**: 설계 및 실행 → 워크플로우 설계

**조립할 그래프**

```
start ─→ DB 조회 ─→ JS 위험도 계산 ─→ Gateway ─┬─(저위험)──────────────┐
                                                 │                        ↓
                                                 └─(고위험)→ Approval ─→ HTTP 권한 반영 ─→ end
```

노드를 하나씩 올리면서 각각의 기능을 설명한다. **이 장면이 시연의 절반이다. 서두르지 않는다.**

### 3-1. DB 조회 노드 (service)

- `plugin_id`: `connector.db.mongodb.query`
- `credential_id`: 장면 2에서 만든 `hr-db`
- `database`: `demo_hr`, `collection`: `employees`, `operation`: `find`
- `filter`: **`{}`** (아래 설명 참고)
- `outputPath`: `hr`

> "결과가 `data.outputs.hr`에 들어가고, 다음 노드들이 이걸 읽습니다."

⚠️ **`filter`에 신청자 사번을 넣을 수 없다.** Service 노드 설정은 정적이라 실행 입력값을
참조하지 못한다 (PXM-45). 그래서 전체를 조회하고 다음 JS 노드에서 신청자를 골라낸다.
시연 데이터가 3건이라 가능한 방식이며, 질문이 나오면 제약을 그대로 설명한다.

**미리 답할 것**: 현재 DB 커넥터는 MongoDB이고 `find`/`findOne` 읽기만 지원한다.
쓰기와 다른 DBMS는 플러그인으로 확장하는 구조다 (장면 3-6에서 이어서 설명).

### 3-2. JS 노드 (script)

조회 결과와 신청 내용으로 위험도 점수를 계산한다.

```js
const rows = context.data.outputs.hr.rows;
const req = context.data.formData;
const me = rows.find(r => r.emp_id === req.emp_id);
if (!me) { throw new Error('직원 정보를 찾을 수 없습니다: ' + req.emp_id); }
let score = 0;
if (req.privilege_level === 'admin') score += 50;
if (me.employment_type === 'partner') score += 30;
if (!me.security_training_done) score += 20;
console.log('applicant=' + me.name + ' score=' + score);
return score < 50 ? 'AUTO' : 'REVIEW';
```

- `outputPath`: **`formData.risk_level`**

> "복잡한 판정 로직을 노드로 다 그리지 않고 여기서 처리합니다."

**말할 것**: 샌드박스에서 실행된다. `input`, `context`, `console`만 주입되고 `require`와
`process`는 없다. `eval`과 `Function` 생성자도 막혀 있다. 타임아웃 기본 1초.

⚠️ **`outputPath`를 `formData.risk_level`로 두는 것이 중요하다.** 게이트웨이 조건식은
`data.formData`의 최상위 필드만 읽고 `data.outputs`는 보지 못한다 (PXM-42).
연산자는 `==`, `!=`, `>=`, `<=`, `>`, `<`를 지원하며 문자열·숫자·불리언을 비교한다.
자세한 제약은 `docs/features.md`의 "게이트웨이 조건은 formData만 읽는다" 참고.

### 3-3. Gateway (exclusive)

- 조건: `risk_level == AUTO` → 자동 승인 경로
- 나머지 → 결재 경로 (`is_default`)

> "게이트웨이는 배타(하나만) / 병렬(전부 분기 후 조인) / 포함(조건 만족하는 전부) 세 가지입니다."

병렬 게이트웨이는 여기서 말로만 언급하고, 여유가 있으면 캔버스에 잠깐 그려 보여준다.

### 3-4. Approval 노드

- `결재라인 입력 방식`: **`고정`** — 승인자 `approver1` 선택
- 승인자 유형에서 `외부 이메일`을 골라 **협력사 관리자**를 한 명 추가

> "사람이 승인해야 하는 지점입니다. PXM 계정이 있는 승인자는 결재함에서 처리하고,
> 계정이 없는 협력사 담당자에게는 일회용 링크와 OTP를 메일로 보냅니다."

**말할 것**: 순차 다단계, 단계별 복수 승인자, ALL/ANY 조건을 지원한다. 결재선을
**실행 요청에서 동적으로 받는 방식**(`결재라인 입력 방식: 동적`)도 있어서, 외부 시스템이
자기 결재선을 그대로 넘겨줄 수 있다.

**미리 답할 것**: 승인 기한과 위임·대결은 아직 없다. 로드맵 최우선 항목이다.

### 3-5. HTTP 노드 (service)

- `plugin_id`: `builtin.http_request`
- `credential_id`: `access-control-api` (`authorization_header`로 주입된다)
- `method`: `GET`, `url`: `http://127.0.0.1:3020/health`
- `outputPath`: `provisioning`

> "승인 결과를 접근제어 시스템에 반영합니다."

⚠️ **`url`과 `body`에도 실행 입력값을 넣을 수 없다** (PXM-45). 지금은 고정 호출만 가능해
"누구에게 무슨 권한을 부여할지"를 외부로 전달하지 못한다. 시연에서는 연동이 일어난다는
것까지만 보여주고, 질문이 나오면 제약을 설명한다.

응답은 `{status_code, ok, headers, body}` 구조로 `data.outputs.provisioning`에 저장된다.

### 3-6. 확장 구조 한 마디 (30초, 화면 전환 없이)

> "여기 붙은 노드들은 전부 플러그인입니다. 오라클이든 사내 ITSM이든 커넥터를 만들어 끼우는 구조고,
> Engine을 고치지 않습니다."

**화면**: 플랫폼 설정 → 플러그인 등록 / 플러그인 제어를 스치듯 보여준다.
`builtin` / `hosted` / `external_http` 세 유형과 플러그인별 사용 통제가 있다는 것만 전달한다.

## 장면 4 — 배포 (2분)

> "설계와 공개는 분리되어 있습니다."

**화면**: 워크플로우 관리

**보여줄 것**
- `DRAFT` 상태에서 저장 → 배포 → `PUBLISHED`
- 버전 목록과 롤백 버튼
- 중지(`DISABLED`) 후 재활성화

**말할 것**: 외부 실행·API Key·스케줄은 **배포된 버전만** 실행한다. 이미 시작한 인스턴스는
시작 시점 버전의 그래프를 끝까지 사용하므로, 배포해도 진행 중인 건이 흔들리지 않는다.

**미리 답할 것**: 반대로 진행 중인 인스턴스를 새 버전으로 옮기는 기능은 없다.

---

## 장면 5 — 웹으로 실행 (5분)

> "이제 실제로 신청해 봅니다."

**화면**: 요청 및 결재 → 요청하기 (신청자 계정으로)

**흐름**
1. `requester1`로 로그인 → 요청하기에서 워크플로우 선택 → 신청 내용 입력 → 실행
2. **고위험 값으로 넣어 결재 경로를 타게 한다**
3. 실행 모니터링 → 해당 인스턴스 → 실시간 추적
   - **여기가 핵심 장면이다.** trace에서 노드마다 남은 `output`을 짚어가며
     DB 조회 결과 → JS 계산 결과 → 게이트웨이가 고른 경로를 순서대로 보여준다
   - 지금 `WAITING`이고 어느 노드에서 왜 멈춰 있는지 설명
4. `approver1`로 전환 → 내 결재함 → 승인
5. 신청자 화면에서 상태가 **새로고침 없이** 바뀌는 것 (SSE)
6. 협력사 승인자 메일함(Mailpit)에서 일회용 링크 → OTP → 승인

**말할 것**: 브라우저로 오는 이벤트는 별도 채널이 아니라 DB에 append된 이벤트 로그를
그대로 흘려보내는 것이다. 그래서 화면이 죽어도 이력이 사라지지 않는다.

## 장면 6 — API로 실행 (5분)

> "지금까지는 웹으로 했지만, 외부 시스템은 웹 없이 같은 워크플로우를 씁니다."

### 6-1. API Key 발급

**화면**: 사용자 및 권한 → 서비스 계정 / API Key

- 서비스 계정 생성 → API Key 발급
- **scope 선택**: `workflow:read`, `workflow:execute` (`task:approve`는 주지 않는다)
- **워크플로우 접근 정책**: `그룹 전체` vs `선택한 워크플로우만`
- IP allowlist, rate limit, 만료 설정
- **발급 직후 1회만 표시되는 원문**을 복사

### 6-2. 외부 소비자처럼 호출

**화면**: api-playground (`http://localhost:5175`)

- API Key만 붙여넣고 접속 (세션 쿠키 없음)
- 허용된 워크플로우 목록 조회 → 실행
- 실행 결과와 trace 조회
- **API Console 탭에서 그대로 복사 가능한 cURL** 제시

> "고객사나 사내 포털은 이 화면이 하는 걸 자기 코드로 하면 됩니다."

### 6-3. 권한이 막히는 것도 보여준다

- `workflow:execute`를 뺀 키로 실행 시도 → `403`과 `MISSING_SCOPE`, 필요한 scope 안내
- 응답의 `request_id`가 응답 헤더·서버 로그와 같은 값인 것

> "장애 문의가 오면 이 ID 하나로 서버 로그를 찾습니다."

**말할 것**: 공개 API는 `/api/v1`이고 Swagger UI가 `/api/docs`에 있다. OpenAPI 3.1 스펙을
그대로 받아 클라이언트를 생성할 수 있다.

**미리 답할 것**: 클라이언트 SDK는 따로 제공하지 않는다. 스펙에서 생성하는 방식이다.

## 장면 7 — 운영과 감사 (3분)

> "돌려놓고 끝이 아니라, 안 돌아갈 때 뭘 볼 수 있는지가 중요합니다."

**화면**: 운영 → 운영 상태 / 실행 이상 점검 / 감사 로그

- **운영 상태**: Job 적체, 장시간 `WAITING`, 만료된 잠금, Webhook 전송 적체를 한 화면에서.
  `HEALTHY` / `WARNING` / `DANGER` 판정과 안전한 재처리 버튼
- **실행 이상 점검**: 런타임 무결성 scan → repair
- **감사 로그**: 장면 1·2에서 만든 그룹·사용자·자격증명 작업이 그대로 기록된 것
- **결과 Webhook**: 결재 결과를 외부로 밀어주는 경로와 재전송 이력

## 장면 8 (선택) — 실패와 복구 (3분)

시간이 남으면 반드시 넣는다. **실패를 보여주는 데모가 신뢰를 얻는다.**

- HTTP 노드의 대상 URL을 죽은 주소로 바꿔 실행
- trace에 재시도가 백오프 간격으로 쌓이는 것
- 최종 `FAILED` 후 인스턴스 재시도 preview → 실패 지점부터 재시도

> "노드 실패는 지수 백오프와 지터로 재시도하고, 소진되면 인스턴스가 실패로 남습니다.
> 원인을 고친 뒤 실패 지점부터 다시 실행할 수 있습니다."

---

## 시연 중 하지 말 것

- **없는 기능을 "곧 됩니다"로 넘어가지 않는다.** 개발팀장 청중은 이걸 정확히 기억한다.
  `docs/features.md` 8장의 미지원 목록을 시연 전에 다시 읽는다.
- 실패할 것이 확실한 버튼을 누르지 않는다.
- 정리되지 않은 테스트 데이터가 보이는 화면을 열지 않는다 (`roadmap.md` R-03).
- 노드를 기능 목록처럼 하나씩 나열하지 않는다. 항상 "이게 왜 필요한가"를 먼저 말한다.

| BPMN 2.0 표준 지원하나요? | 아니오. 독자 JSON 포맷입니다. 표준 호환을 요구하는 요건이 나오면 그때 검토합니다 |
| 오라클/PostgreSQL 붙나요? | 현재 DB 커넥터는 MongoDB 읽기 전용입니다. 다른 DBMS는 플러그인으로 만들어 끼웁니다 |
| 승인자가 휴가면요? | 위임·대결은 아직 없습니다. 로드맵 최우선 항목입니다 |
| 3일 지나면 자동으로 어떻게 되나요? | 승인 기한과 에스컬레이션은 아직 없습니다. 위와 같은 우선순위입니다 |
| 노드에서 에러 나면 다른 경로로 못 가나요? | 에러 분기 엣지는 없습니다. 재시도 후 인스턴스가 실패로 남고 운영자가 재시도합니다 |
| 반복 처리(결재 대상 N건)는요? | Multi-instance는 지원하지 않습니다. 현재는 워크플로우를 N번 실행하는 방식입니다 |
| SSO 되나요? | 아직 로컬 계정만 지원합니다 |
| 성능은 어느 정도인가요? | 이전 측정 기록이 `docs/old/workflow-runtime-speed-test.md`에 있습니다. 최신 구조에서는 다시 측정해야 합니다 |
| 멀티테넌시 되나요? | 그룹 단위 격리까지입니다. 테넌트 분리는 없습니다 |
| SaaS로 쓸 수 있나요? | 현재는 온프레미스 설치형 기준입니다 |
