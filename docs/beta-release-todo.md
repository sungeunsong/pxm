# 0. 제품 결정

## DEC-01. 제품 포지션 확정

- [!] PXM의 1차 포지션을 `API-first/headless workflow`로 확정한다.
- [ ] 외부 공개 API와 내부 관리 콘솔 API의 경계를 목록으로 작성한다.
- [ ] 신청자·승인자 UI 중 PXM이 직접 제공할 범위와 고객사가 구현할 범위를 명시한다.

완료 조건:

- 제품 소개 한 문장, 베타 대상 사용자, 제외 범위가 서로 모순되지 않는다.
- 범용 BPM 제품을 목표로 바꾸면 현재 제외 항목과 우선순위를 다시 검토한다.

## DEC-02. 첫 베타 공개 수준 확정

- [!] `통제된 데모 / 초대 기반 비공개 베타 / 공개 베타` 중 첫 목표를 선택한다.
- [ ] 베타 참여 대상, 인원 또는 고객 수, 기간, 지원 범위를 기록한다.
- [ ] 베타에서 수집할 피드백과 성공 판단 기준을 정한다.

## DEC-03. 사용자 체감형 와우 포인트 선정

- [!] 실제 신청자·승인자 또는 연동 개발자가 반복해서 겪는 핵심 문제 하나를 선택한다.
- [ ] 문제를 PXM 사용 전과 사용 후로 비교해 한 문장으로 설명한다.
- [ ] 발표할 기능이 실제 베타 기능과 같은 데이터·권한·실행 경로를 사용하는지 확인한다.
- [ ] 관리자용 Flow Designer 관제 연출만으로 와우 포인트를 구성하지 않는다.

완료 조건:

- 고객 가치가 한 문장으로 설명된다.
- 발표자가 설명하지 않아도 화면 변화 또는 결과로 가치가 드러난다.
- 가짜 통계, 하드코딩 성공 결과, 발표 전용 우회 로직이 없다.

# 1. API 계약 P0

## API-01. 인증 실패 상태 코드 수정

- [x] 잘못된 API Key를 `401`로 반환한다.
- [x] 만료·비활성 API Key도 `401`로 반환하고 사유를 메시지 또는 오류 코드로 구분한다.
- [x] 형식 오류에만 `400`을 사용한다.
- [x] 단위 테스트를 추가한다.

완료 조건: 잘못된 키, 만료 키, 비활성 키 회귀 테스트가 모두 통과한다.

## API-02. 권한 부족과 리소스 은닉 구분

- [x] 읽을 수 있는 워크플로우에 실행 scope만 없으면 `403`을 반환한다.
- [x] 응답에 필요한 scope를 식별할 수 있는 오류 코드를 포함한다.
- [x] 다른 그룹처럼 존재를 숨겨야 하는 리소스는 `404`를 유지한다.
- [x] `docs/api-consumer-demo.md`의 계약과 테스트를 일치시킨다.

완료 조건: `읽기 가능+실행 불가=403`, `타 그룹=404`가 자동 테스트로 고정된다.

## API-03. 선택적 POST body의 500 제거

- [x] `POST /templates/:id/deploy`를 body 없이 호출해도 정상 동작하게 한다.
- [x] 선택적 body를 받는 다른 POST 컨트롤러를 전수 검색한다.
- [x] body 없음, `{}`, 유효 body, 잘못된 body 테스트를 추가한다.

완료 조건: 사용자 입력 때문에 처리되지 않은 `TypeError`와 500이 발생하지 않는다.

## API-04. 워크플로우 접근 정책 명시화

- [x] 아래 모델 또는 동등하게 명시적인 모델을 확정한다.

```text
workflow_access: "all_in_group" | "allowlist"
allowed_workflow_ids: [...]
```

- [x] `all_in_group`은 이후 추가된 같은 그룹 워크플로우를 동적으로 허용한다.
- [x] `allowlist`의 빈 배열은 아무 워크플로우도 허용하지 않는다.
- [x] API Key 발급·회전·조회 UI와 API에 같은 의미를 적용한다.
- [x] 기존 Key 마이그레이션 정책을 정한다. 기존 레코드는 권한 확대 없이 `allowlist`로 해석한다.
- [x] 그룹 밖 리소스와 scope 부족 응답 원칙을 API-02와 일치시킨다.

완료 조건: Key 발급 후 새 워크플로우를 생성하는 회귀 시나리오가 정책별로 통과한다.

## API-05. 외부 API v1 경로 도입

- [x] 외부 공개 API는 `/api/v1`으로 제공하고 베타 마이그레이션 동안 공개 기능의 기존 `/api` 경로를 병행한다. 내부 관리 API는 `/api`만 유지한다.
- [x] 외부 공개 endpoint 목록을 확정한다. `docs/public-api-v1.md`를 기준으로 한다.
- [x] Web, api-playground, E2E, health check, 운영 스크립트의 영향을 반영한다. Web·health check는 관리/내부 경로이므로 기존 `/api`를 유지하고 api-playground만 `/api/v1`로 전환한다.
- [x] 외부 문서와 예제에는 버전 경로만 사용한다.

완료 조건: 기존 관리 콘솔 회귀 없이 `/api/v1` 공개 계약 테스트가 통과한다.

## API-06. 표준 오류 응답과 correlation id

- [ ] 서버가 모든 요청에 correlation id를 생성하거나 유효한 `x-request-id`를 수용한다.
- [ ] 식별자를 응답 헤더, 오류 응답, 애플리케이션 로그에 동일하게 기록한다.
- [ ] 전역 exception filter로 공개 API 오류 형식을 통일한다.
- [ ] 500 응답에는 내부 정보나 stack trace를 노출하지 않는다.

완료 조건: 고객이 전달한 correlation id 하나로 해당 서버 로그를 찾을 수 있다.
