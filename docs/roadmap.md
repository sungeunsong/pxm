# PXM 남은 작업

현재 지원 기능은 `docs/features.md`에 있다. 이 문서는 **아직 하지 않은 일**만 다룬다.

## 전제 (2026-09-03 갱신)

우선순위는 전부 아래 전제에서 나온다. 전제가 바뀌면 순서도 다시 잡는다.

1. **첫 청중은 사내 연구소, 특히 개발팀장이다.** 외부 고객 대상 베타가 아니다.
2. **시연 목적은 우리가 지원하는 기능 전반을 보여주는 것이다.** 자격증명 관리, 사용자·그룹,
   워크플로우 노드 구성, API Key 발급과 사용까지 한 시나리오에 엮어서 보여준다.
   각본은 `docs/demo-scenario.md`에 있다.
3. **소재는 접근제어 권한 신청이다.** 우리 접근제어 솔루션의 결재 기능을 PXM으로 대체할 수
   있는지가 자연스럽게 함께 검증된다. 외부 고객 후보는 아직 없고 이 사내 사례가 1호 후보다.
4. **API-first는 확정이 아니다.** API를 주력으로 설계했지만 웹 전용 사용도 배제하지 않는다.
   이 결정은 시연 결과를 보고 내린다.
5. **배포 형태는 온프레미스 설치형이다.** SaaS는 이후 고려 사항이다.

이 전제 때문에 **외부 베타 운영 준비(지원 채널, 비상 연락망, 장애 공지, 인증서 만료 알림)의
우선순위는 낮아졌다.** 대신 시연 시나리오가 처음부터 끝까지 실제로 돌아가는 것이 최우선이다.

이전 전제(서드파티 대상 비공개 베타)로 작성된 문서는 `docs/old/`에 보관되어 있다.

# P0 — 시연을 막는 것

## R-0A. `pnpm gate:beta`가 통과하지 않는다 (완료, PXM-43)

브라우저 회귀가 PXM-31 이후 계속 red였다. 런타임 결함이 아니라 E2E가 결재·종료 확인창을
처리하지 않은 채 통과하고 있었다. 검증이 "목록으로 돌아왔는가"뿐이라 접수 실패를 놓쳤다.

- [x] 원인 판별 (런타임 정상, 테스트가 UI 변경을 따라가지 못함)
- [x] 확인창 처리와 성공 토스트 검증으로 교체
- [x] `gate:beta` 통과 — Engine 37, 브라우저 E2E **12/12**

`serial` 모드 때문에 전체 테스트가 12개인 것도 이번에 드러났다.
E2E 하네스가 인프라 기동 실패와 테스트 실패를 구분하지 못하는 문제는 PXM-44로 분리했다.

## R-00. HTTP 노드가 응답 본문을 버린다 (완료, PXM-35)

`builtin.http_request`의 Engine 실행 경로가 응답 상태코드만 확인하고 본문을 읽지 않았다.
디자이너의 "노드 테스트"는 API 경로를 타서 본문을 정상 반환했기 때문에 문제가 가려져 있었다.

- [x] 응답 본문을 읽어 `output`에 담는다
- [x] API 노드 테스트와 같은 계약(`status_code`, `ok`, `headers`, `body`)을 사용한다
- [x] 응답 크기 상한(기본 256KB, `HTTP_RESPONSE_BODY_LIMIT_BYTES`)과 초과 시 절단 표기
- [x] `content-type` 기반 JSON 파싱과 실패 시 원문 유지
- [x] 단위 테스트 6건과 실제 HTTP 왕복 테스트 2건 추가
- [x] `docs/features.md`의 내장 커넥터 표와 디자이너 도움말 갱신

## R-01. 시연 시나리오를 실제 워크플로우로 구성 (완료, PXM-38)

- [x] DB 조회 → JS 위험도 계산 → Gateway 분기 → Approval → HTTP 호출 그래프를 구성한다
- [x] 자동 승인 경로와 결재 경로 양쪽이 모두 끝까지 실행되는지 확인한다
- [x] 반려 경로와 외부 이메일 OTP 승인도 확인한다
- [x] 현재 노드로 표현되지 않는 요구사항을 목록으로 남긴다 → **PXM-45**, PXM-42

완료 조건: 필요한 승인·반려 조작 외에 DB나 워크플로우를 수동으로 고치지 않고
세 경로가 완주한다. (2026-09-04 확인)

**단, 검증 증거는 개발 DB에만 있다.** DB를 초기화하면 재현 근거가 사라진다.
자동화된 증거는 R-06(PXM-39) 또는 seed(PXM-37) 이후에 생긴다.

## R-02. 데모 데이터 seed / reset

발표 직전마다 DB를 손으로 정리하지 않도록 한 명령으로 준비한다. 발표 사고의 가장 흔한 원인이다.

- [ ] `demo:seed`: R-01 시나리오에 필요한 그룹·사용자·워크플로우를 같은 상태로 생성
- [ ] `demo:reset`: 이전 실행·결재·Webhook 흔적을 정리하고 다시 seed
- [ ] 고정 운영 Secret이나 재사용 가능한 API Key 원문을 저장하지 않는다
- [ ] 실행 후 발표에 필요한 리소스 ID와 접속 경로를 요약 출력한다

완료 조건: 깨끗한 개발 DB에서 seed 후 R-01 시나리오가 수동 수정 없이 실행된다.

## R-03. 테스트 데이터와 설계 메모 제거

- [x] 개발 DB 초기화 (2026-09-04). `pxm_db`를 드롭하고 인덱스를 재생성했다.
      테스트 그룹, Smoke 워크플로우, 점검 계정이 모두 사라졌다.
- [ ] `운영자 / 모니터링 담당 상세 화면 구성` 같은 화면 안 설계 메모를 제품 문구로 교체

DB는 비웠지만 **코드에 남은 문구는 그대로다.** 화면 정리는 R-04·R-05에서 함께 처리한다.
초기화 이후 남긴 기준 데이터는 그룹 `보안운영팀`, 계정 `admin`/`secadmin`/`approver1`/`requester1`,
자격증명 2건, `demo_hr.employees` 3건, 워크플로우 `협력사 접근 권한 신청`이다.

## R-04. 시연 화면의 UI 결함 수정

시연 범위가 기능 전반으로 넓어지면서 **아래 결함이 있는 화면이 시연 첫 4분에 등장한다.**
이전에는 우선순위가 낮았지만 지금은 P0다.

- [ ] 사용자 및 권한(장면 1): 저장 버튼이 탭 줄과 겹친다
- [ ] 사용자 및 권한(장면 1): 선택한 그룹이 카드와 목록에 중복 표시된다
- [ ] 연동 자격증명(장면 2): 헤더 제목이 1600px 폭에서 2줄로 깨지며 우측 사용자 영역까지 밀린다

발표 해상도를 미리 고정하고 그 해상도에서 확인한다.

## R-05. 시연 경로 전체 점검

`docs/demo-scenario.md`의 모든 장면을 실제로 클릭하며 확인한다. 시연에서 여는 화면이
장면 1·2·3·4·5·6·7로 늘어났으므로, 지금까지 열지 않던 화면이 시연 경로에 들어왔다.

- [ ] 플러그인 등록 / 플러그인 제어 화면(장면 3-6)에 죽은 버튼이나 설계 메모가 없는지
- [ ] 서비스 계정과 API Key 발급 화면(장면 6-1)의 문구가 역할과 맞는지
- [ ] 실행 이상 점검 화면(장면 7)이 정상 상태에서 정직한 empty state를 보이는지
- [ ] 각 화면에서 클릭 가능한 모든 요소가 실제로 동작하는지

## R-06. 시연 시나리오 회귀 테스트

- [ ] R-01 시나리오를 브라우저 E2E로 자동화한다
- [ ] 빈 화면, 죽은 버튼, 권한 오류가 없는지 확인한다
- [ ] 시연 직전 실행할 단일 명령을 package script로 제공한다

완료 조건: `demo:reset` → `demo:seed` → 시나리오 실행이 한 번에 통과한다.

# P1 — 공개 API 계약 마무리

지금 고치지 않으면 나중에 breaking change가 되는 항목이다. 외부 공개 시점과 무관하게 지금 정한다.

## R-07. 인스턴스 취소를 공개 API v1에 노출 (결정됨)

현재 `POST /instances/:id/terminate` · `pause` · `resume`에 `@Version`이 없어
공개 `/api/v1`에 나오지 않는다 (`apps/api/src/instances/instances.controller.ts:107-126`).
**외부 시스템이 워크플로우를 시작할 수는 있는데 취소할 수 없다.** 신청자의 "취소"는 결재의 기본 동작이다.

- [ ] `terminate`를 `/api/v1`에 노출한다
- [ ] `pause` / `resume`을 공개할지 결정한다 — 운영자용 개념이라 제외해도 무방하다
- [ ] Swagger DTO와 오류 응답을 붙이고 `openapi.json`을 재생성한다
- [ ] `docs/public-api-v1.md`와 `docs/features.md`를 갱신한다

## R-08. 공개 API 표면의 나머지 불일치 정리

- [ ] `POST /tasks/:id/hold`가 관리 경로에만 있다. 승인·반려는 v1인데 보류만 빠져 일관성이 깨진다
- [ ] Webhook 엔드포인트 자체 등록이 콘솔 전용이다. 결과를 받으려면 사람이 웹에 들어와야 한다
- [ ] 템플릿 생성·수정을 API로 열지 결정한다. "워크플로우도 API로 만들 수 있냐"는 반드시 나오는 질문이다

# P2 — 결재 제품으로서 부족한 것

R-01에서 접근제어 결재를 옮겨보면 대부분 여기서 막힌다. 사내 데모 이후의 개발 우선순위다.

## R-09. 승인 기한과 에스컬레이션

- [ ] Approval 노드에 기한을 설정하고, 초과 시 독촉·자동 반려·상위자 상신 중 하나를 수행한다

없으면 "3일 지나면 어떻게 되냐"는 질문에 답할 수 없다.

## R-10. 위임과 대결(代決)

- [ ] 승인자가 부재중일 때 다른 사람이 처리하도록 Task 소유자를 바꾼다

**API-first라 해도 고객사가 자기 UI로 해결할 수 없는 기능이다.** Task 소유자 변경은 엔진 상태
변경이므로 PXM이 제공해야 한다. R-09와 함께 결재 제품의 최소 요건으로 본다.

## R-11. 그 밖의 미지원 기능 판단

`docs/features.md` 8장의 미지원 목록 중 무엇을 로드맵에 넣을지 R-01 결과를 보고 정한다.
BPMN 2.0 XML은 표준 호환을 요구하는 고객이 나오기 전까지는 착수하지 않는다.

# 온프레미스 설치 전 필수 확인

배포 형태가 온프레미스이므로 아래는 **설치 대상 환경마다** 확인한다. SaaS 운영 항목과 달리
이건 미룰 수 없다.

- [ ] 기본 관리자 비밀번호(`admin`/`admin1234`) 제거 — `PXM_BOOTSTRAP_ADMIN_PASSWORD` 설정
- [ ] MongoDB 인증 활성화, Docker internal network 전용, 호스트 포트 비공개
- [ ] DB·Credential·외부 결재·SMTP Secret을 환경변수로 외부 주입
- [ ] 암호화 일일 백업 scheduler와 보존 정책
- [ ] 별도 namespace 복원 검증 (`pnpm ops:restore:verify`)
- [ ] API·Engine 강제 종료 복구와 중복 실행 방지 리허설 (`pnpm ops:rehearse`)
- [ ] 배포 메타데이터 dry-run (`pnpm db:workflow-publish-metadata:repair`)
- [ ] 같은 커밋에서 `pnpm gate:release` 통과

절차는 `docs/production-beta-runbook.md`를 따른다.
